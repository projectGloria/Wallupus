# Wallupus: Code Audit (2026-11-22)

Scope: the whole repository at `52297b3`. That covers every Kotlin source file under `app/src/main/java/dev/wallupus/`, the tests, the manifest and resources, `config.json` and `doh-bypass.txt`, the Gradle build, verification metadata and CI.

Method: a manual read of every file, checked against the invariants in `AGENTS.md`. I also ran `.\gradlew.bat test assembleDebug` with JDK 17. **It passed: BUILD SUCCESSFUL, all 55 unit tests green.**

Nothing in this audit has been changed in the code. Every item below is a finding or a proposal.

---

## 1. Executive summary

Wallupus is in unusually good shape for a personal project:

- The hard parts are done carefully: the packet loop, cache coherence, list updates and the privacy posture.
- The invariants documented in `AGENTS.md` are actually upheld in the code.
- Failure modes are mostly designed for, not just hoped about.

The real risks cluster in three places:

1. **Crash surface in background coroutines.** Any non-`IOException` thrown inside a `scope.launch` or `appScope.launch` has no handler and kills the process, and with it DNS for the whole phone. This is the single most important fix.
2. **Network transitions.** Nothing reacts to Wi-Fi/cellular handover. Pooled DoH connections go dead and the first queries after a switch stall for the 3 s timeout. Separately, the Private DNS conflict warning goes stale.
3. **Edge-of-protocol behaviour.** There is no TC/EDNS handling, port-53 TCP is reset, trapped IPs get no ICMP reply, and failover is sequential. None of these is a bug in the common case, but each produces a "the internet feels weird" moment that is hard to diagnose.

The rest is polish: UI nits, CI hardening, test gaps, stale dependencies and repository hygiene.

| Severity | Count | Theme |
|---|---|---|
| High | 2 | Uncaught coroutine exceptions; no network-change handling |
| Medium | 7 | Private DNS staleness, TCP/53, TC bit, SourceCheck pinning, failover latency, export cancellation, keystore escaping |
| Low | ~20 | Listed per section |
| Ideas | ~20 | Section 9 |

## 2. Packet path and VPN (`vpn/`)

### H1: An uncaught exception in an upstream coroutine crashes the app *(High)*

[`PacketLoop.kt:65`](../app/src/main/java/dev/wallupus/vpn/PacketLoop.kt#L65) builds the scope as:

```kotlin
CoroutineScope(SupervisorJob() + Dispatchers.IO.limitedParallelism(MAX_PARALLEL))
```

There is no `CoroutineExceptionHandler`.

- A `SupervisorJob` stops one failed child from cancelling its siblings. It does **not** swallow the exception: an unhandled exception in a `launch` goes to the thread's default handler, which on Android kills the process.
- The reader thread's `catch (e: RuntimeException)` at `:138` covers only `handle()` itself, not the work it launches at `:189`.

Things that can throw inside that `launch`:

- `DohClient.post` catches only `IOException` ([`DohClient.kt:150`](../app/src/main/java/dev/wallupus/dns/DohClient.kt#L150)). OkHttp throws `IllegalStateException` and `IllegalArgumentException` in several corner cases: a malformed header from a hostile or broken server, a pool shut down mid-call, or `toHttpUrl` on a later custom edit. Under some interceptors it can also throw `SecurityException`.
- `DnsMessage.isResponseFor` and `withId` run on an arbitrary upstream reply. They are written defensively, but a single missed bounds check becomes an `ArrayIndexOutOfBounds` and a crash, not a dropped packet.
- `PlainDnsClient.resolve` has the same exposure.
- `WallupusApp.appScope` ([`WallupusApp.kt:32`](../app/src/main/java/dev/wallupus/WallupusApp.kt#L32)) has the same shape with no handler. It runs `evictAll` and other background work.

Impact: this breaks the first hard rule in AGENTS.md ("one failure must never kill DNS for the phone"). If the app process dies, the VPN dies with it. Always-On restarts it eventually, but in the meantime apps see no DNS, or leak to the network's resolver.

**Fix:**

- Add a `CoroutineExceptionHandler` that logs to both scopes.
- In the launched block, catch `Exception` around the resolve. On failure, answer SERVFAIL, so the client is never left waiting for 5 s:

```kotlin
val handler = CoroutineExceptionHandler { _, e -> Log.w(TAG, "upstream task failed", e) }
private val scope = CoroutineScope(SupervisorJob() + Dispatchers.IO.limitedParallelism(MAX_PARALLEL) + handler)
...
scope.launch {
    try {
        val answer = try { ... } catch (e: Exception) { DnsMessage.servfail(udp.payload, q) }
        reply(udp, answer)
    } finally { inflight.release() }
}
```

- Also widen `DohClient.post`'s catch to `Exception`, but rethrow `CancellationException`.

### M1: TCP to the fake resolver on port 53 is reset *(Medium)*

`handle()` resets every non-UDP packet. That includes TCP/53 to `10.111.222.1`. DNS over TCP is mandatory (RFC 7766). Clients fall back to TCP when they receive TC=1, and some stub resolvers and tools (`dig +tcp`, a few game launchers, some VPN-in-VPN setups) use it directly.

There is no userspace TCP stack, and that is a deliberate choice. The consequence is that any answer larger than the client's UDP buffer cannot be delivered at all (see M2).

Options, cheapest first:

1. Never set TC on replies to the tun: hand back the full response. The tun MTU is 16384 and the reply builder handles up to 65,507 bytes. The client's UDP buffer is the only limit, and the bionic and netd resolvers accept large UDP datagrams in practice.
2. A minimal TCP/53 responder: SYN → SYN-ACK, a single 2-byte-length-prefixed query → reply → FIN. This is about 150 lines in `IpPacket` and needs no general stack. It is the "correct" fix.

### M2: No TC or EDNS awareness *(Medium)*

DoH upstreams answer over HTTPS, so their responses can be large (DNSSEC, big TXT records, HTTPS/SVCB records). The loop forwards them verbatim over UDP:

- If the client's query had no OPT record, it advertised a 512-byte limit. A larger reply technically violates its expectation. Most stubs accept it anyway. Some, such as older embedded libs and Go's pure resolver in strict mode, discard it and retry.
- Conversely, when `PlainDnsClient` gets TC=1 from the network resolver, the truncated reply is passed through. The client then retries over TCP and hits M1's RST, so **the name fails to resolve**.

Fixes:

- In `PlainDnsClient`, retry over TCP to the upstream on TC=1. This is cheap, because the app's own sockets bypass the tun.
- Forward the full answer to the client regardless of its advertised size (pragmatic).

### L1: Trapped IPs give no ICMP response *(Low)*

Routing the anycast IPs of public resolvers (`8.8.8.8`, `1.1.1.1`, …) into the tun is a good trick to stop hardcoded DoT and DoH. Some side effects follow:

- `ping 8.8.8.8` and plain ICMP connectivity checks used by some apps and routers hang instead of failing fast.
- UDP to trapped IPs on ports other than 53 (QUIC/HTTP3 to `1.1.1.1:443`, DoQ on `:853`/`:8853`) is dropped silently, so the client waits out its full timeout before falling back.

Fix: answer with ICMP Port Unreachable for UDP, and ICMP Echo Reply (or Unreachable) for ICMP. This mirrors `buildTcpReset`: fast failure means a fast fallback.

### L2: Sequential endpoint failover can exceed the client's timeout *(Low)*

[`DohClient.kt:97`](../app/src/main/java/dev/wallupus/dns/DohClient.kt#L97) tries endpoints one after another, with a call timeout of 4 s each (`:46-48`).

- With 2–3 endpoints and the preferred one blackholed, the second attempt starts at about 4 s. That is after the bionic resolver's first retry (about 5 s total, with retries around 1–2 s depending on the version).
- The client gives up or retries, which creates *another* in-flight query. Under a dead upstream, this snowballs toward the 64-query SERVFAIL cap.

Improvements:

- Lower the first-attempt call timeout to about 2 s. Alternatively, race (happy-eyeballs style): start endpoint #2 after 300–500 ms if #1 hasn't answered, and take whichever arrives first.
- Remember a failing endpoint for N seconds (circuit breaker), so not every query pays the timeout.

### L3: No coalescing of identical in-flight queries *(Low)*

Each query that misses the cache launches its own upstream call. A browser opening a page fires A and AAAA, often duplicated across processes (WebView, the app itself, Chrome's prefetch). Under poor connectivity, the duplicates multiply load and eat into the 64-slot semaphore.

Fix: a `ConcurrentHashMap<CacheKey, Deferred<ByteArray?>>` keyed like the cache. The first query creates the `Deferred`, and later ones await it, then each restores its own ID. This also gives a small latency win on the second query.

### L4: Tun close and in-flight writes race *(Low)*

`stop()` closes the tun while coroutines may still be inside `writePacket`. The `IOException` is caught, which is fine.

The remaining race: if a new tunnel is established while the old loop's coroutines are still alive, could a stale `output` stream write into a reused fd number? `FileOutputStream` holds its own `FileDescriptor` object. Once that is closed, the integer is invalid for *this* object, so the stream fails safely. **No action needed**, but `scope.cancel()` before closing the fd in `stop()` would make it obvious.

### L5: IPv6 reply length at the limit *(Low)*

The cap of 65,507 bytes is right for IPv4. In IPv6, the payload-length field counts UDP header + payload, so the limit is 65,527. Replies stay safe as long as the shared `MAX_DNS` keeps both under their limits. Please check that `IpPacket.buildUdpReply` asserts `payload.size <= 65_507` rather than relying on callers. A future code path that skips `DohClient`'s cap (for example `PlainDnsClient` over TCP after M2) would otherwise wrap silently.

### L6: `getConnectionOwnerUid` on the reader thread *(Info)*

This was measured as sub-millisecond, and the design is documented and sound. Under heavy query storms (hundreds per second at app start), this binder call becomes the reader thread's bottleneck. If that ever shows up, cache `(srcPort, srcAddr) → uid` for about 2 s.

### Positives in this area

- Matching runs before the cache lookup. Cache epochs are captured per query, and the generation clear is done only by the reader thread. This is correct and well commented.
- The self-pipe with `Os.poll` for clean shutdown is the right design. `onDied` closes the tunnel instead of leaving a black hole.
- The semaphore answers SERVFAIL instead of queueing.
- RST for DoT/DoH probes gives fast fallback.

## 3. DNS clients and resolvers (`dns/`)

### H2: No reaction to network changes *(High)*

Nothing in the app registers a `ConnectivityManager.NetworkCallback`. Consequences:

1. **Dead pooled connections.** After a Wi-Fi → cellular handover, the OkHttp pool still holds HTTP/2 connections bound to the old network. The next DoH query writes into a dead socket and waits up to the read timeout (3 s). Then OkHttp retries on a new connection. Every handover means a few seconds of "nothing loads". On phones that roam often (commute, office Wi-Fi), this is the most user-visible issue in the app.
2. **`PlainDnsClient` server list.** If the network's DNS servers are read once or on query, check that they come from the *current* default network. With DNS-only-plain mode on a network switch, a stale `LinkProperties` means queries to an unreachable router IP.
3. `VpnService.Builder.setUnderlyingNetworks` is not called. Android then reports the VPN as "metered/unmetered" from the default network, which is fine. Calling it with the current network makes metering and the status bar more accurate, and helps `WorkManager`'s unmetered constraint.

Fix: register a default-network callback in `WallupusVpnService`. On `onAvailable` or `onLinkPropertiesChanged`:

- `client.connectionPool.evictAll()` (on IO);
- refresh the `PlainDnsClient` servers;
- `setUnderlyingNetworks(arrayOf(network))`;
- optionally `cache.clear()` through the existing generation mechanism, since split-horizon names differ per network.

### M3: Private DNS warning goes stale *(Medium)*

`HomeScreen.strictPrivateDnsHost()` is computed in `remember(running)`. If the user follows the warning, turns Private DNS off in system settings and comes back, the warning stays until the tunnel restarts. The reverse also happens: turning strict mode *on* while Wallupus runs shows no warning.

Why it matters: Private DNS strict mode (`dns.google`, `one.one.one.one`) bypasses the tun entirely, so blocking silently stops working. If the strict-mode host's IPs are among the trapped ones, **all DNS fails**, because the system resolver hard-fails in strict mode.

Fix:

- Re-evaluate on `Lifecycle.Event.ON_RESUME` (`LifecycleEventEffect(ON_RESUME)`), or observe it through a `NetworkCallback.onLinkPropertiesChanged` exposed as a `StateFlow`.
- Make the warning actionable: add a button that opens `Settings.ACTION_WIRELESS_SETTINGS` (there is no public deep link to Private DNS).

### L7: `!!` in `Resolvers` *(Low)*

[`Resolvers.kt:55`](../app/src/main/java/dev/wallupus/dns/Resolvers.kt#L55): `listOf(prefs.customUpstream!!)`.

`resolveId` checks `customUpstream != null` first, but it reads the pref a second time here. If the custom upstream is cleared concurrently (Settings and service start racing), this is an NPE in DNS setup.

Fix: read the pref once and pass the value:

```kotlin
private fun current(): Pair<String, List<Upstream>> { val custom = prefs.customUpstream; ... }
```

`id!!` at `:50` is fine (guarded by `any { it.id == id }`), but `requireNotNull(id)` or a smart cast through a local reads better.

### L8: Probe is two sequential round trips with full failover *(Low)*

`probe()` reuses `resolve(r, …)`, which walks every endpoint. A resolver with one dead endpoint out of two still "passes", but reports the latency of the working one plus nothing about the dead one. That is fine for switching, but "Test speed" can be misleading.

Idea: report per-endpoint results in the speed test, and mark resolvers with a dead endpoint.

### Positives

- Probe isolation through a separate `Dns`, so it gets a distinct OkHttp `Address` and the live pool is not polluted. This is subtle and correct.
- Bounded body reads with `source.request(MAX+1)` are exactly right. Redirects are off. Responses are validated (`isResponseFor` plus `isUsableAnswer`).
- Eviction happens on IO, so there is no `NetworkOnMainThread`.
- Bootstrap IPs must be ASCII-digit IP literals, which closes the Arabic-Indic digit trick. That is a thoughtful catch.

## 4. Filtering and lists (`filter/`)

### M4: `SourceCheck` can pin a legitimately shrunk list forever *(Medium)*

The rule "not below ¼ of cached" protects against a truncated or hijacked download. When a maintainer does real cleanup (HaGeZi and others periodically drop dead domains or split lists), the new list fails the check **every day forever**. The old copy keeps being used, and since the validators are not saved, the full list is **re-downloaded daily** (up to 64 MB on unmetered networks).

Fix, any of:

- After N consecutive rejections (say 3 days) with a consistent size (±5 %), accept the new list.
- Show a "Source X shrank from A to B — accept?" action in Lists (needs a `lastUpdateError`-style per-source state).
- Save validators even on rejection, so the next check is a cheap 304 until upstream changes again.

### L9: Hosts lines keep only the first name *(Low, documented trade-off)*

`0.0.0.0 a.com b.com c.com` is valid hosts syntax. `ListParser.kt:51` deliberately keeps only the first name, and a comment there says so. None of the four bundled sources uses multi-name lines, so this costs nothing today. If you ever add custom list URLs (section 9), returning every name from the line becomes worthwhile. Pin the current behaviour with a `FilterTest` case either way.

### L10: Wildcard and modifier lines are skipped *(Low, by design)*

`*.example.com`, `||example.com^$third-party` and `/regex/` are skipped. The rule "skip, never approximate" is correct and documented. `$important` is already accepted (`ListParser.kt:57-61`).

One small extension: `$important` is currently stripped and treated as an ordinary block. In AdGuard semantics it should beat a list `@@` exception. Today a list allow can override an `$important` block, which is rare but the opposite of what the list author meant. `$all` and `$document` are also plain domain blocks for DNS purposes and could be accepted the same way.

### L11: Cache files of removed or disabled sources are never deleted *(Low)*

When a source is removed from `config.json` or disabled, its cached copy and validators stay in `filesDir` forever. That can be tens of MB.

Fix: during `BlocklistUpdater.run`, delete `sources/<id>*` for ids not in the active set.

### L12: Peak memory during compile and load *(Low)*

Building `CompiledLists` collects hashes into a growable list (boxed or a `LongArray` that doubles), then sorts and dedupes, and finally writes. Peak use is about 3× the final size. For 1–2 M entries that is 30–50 MB transient, survivable but noticeable on low-RAM devices, where the update worker may be killed.

Also, loading `blocklist.bin` reads it fully into heap arrays.

Ideas:

- Pre-size from the per-source counts already known.
- `mmap` `blocklist.bin` (`FileChannel.map(READ_ONLY)` → `LongBuffer`) and binary-search directly. Load becomes near-instant, the file is shared through the page cache, and nothing goes on the heap. The atomic file swap still works: open a new mapping, swap the `AtomicReference`, and let the old mapping be collected.

### L13: The FNV-1a 64-bit collision budget *(Info)*

With 2 M entries, the probability that some lookup collides with an entry is about n·m / 2⁶⁴. That is negligible (around 1e-7 over a lifetime of lookups). No action needed, noted for completeness.

### Positives

- Matchers are immutable and swapped through an `AtomicReference`, with lock-free reads.
- Precedence rules are clear and tested. The rule-target cap at the public-suffix boundary is a nice detail.
- "Never make things worse": conditional GETs, size caps, cached fallback, atomic `ATOMIC_MOVE`, and `EMPTY` on corruption.
- Mutex-guarded updates. The unique-work name is preserved, with a comment explaining why.

## 5. Logging and export (`log/`, `ui/LogScreen.kt`)

### M5: Export can be cancelled mid-write *(Medium)*

`exportLog` runs in a composition-bound scope, `rememberCoroutineScope`, on IO. If the user switches tabs or leaves the screen while a 20k-group export is writing, the scope is cancelled:

- the SAF document is left **truncated** without any message;
- the whole CSV is built as one `String` first (about 2–4 MB of strings at peak, then the encoded bytes), so the window is larger than it needs to be.

Fix:

- Run the export in `WallupusApp.appScope`, or in `withContext(NonCancellable)` for the write.
- Stream rows straight into `contentResolver.openOutputStream(uri).bufferedWriter()` instead of building the string.
- Show a snackbar or a "Exported N rows" line, and on failure delete the partial document with `DocumentsContract.deleteDocument`.

### L14: "Clear" has no confirmation *(Low)*

One tap wipes up to 20k groups of RAM-only history, which cannot be recovered. Add a confirm dialog, or an "Undo" snackbar holding the snapshot for 5 s.

### L15: `ClockFormats` is remembered without a key *(Low)*

If the user switches the system's 24-hour setting while the app is in the background, timestamps keep the old format until the process restarts. Key it on `DateFormat.is24HourFormat(context)` read at `ON_RESUME`, or on `LocalConfiguration`.

### L16: `buildLogView` copies the full snapshot at 2 Hz *(Low, performance)*

While traffic flows and the Log tab is visible, each 500 ms tick snapshots up to 20k groups, filters, groups and sorts them on `Dispatchers.Default`. That is correct (off main), but about 2 × 20k allocations per second on a busy phone is measurable battery use.

Ideas:

- Give `QueryGroups` a monotonically increasing `version`. Skip the rebuild when the version is unchanged (idle phone, screen on).
- Rebuild incrementally: only the groups touched since the last version.

### L17: `EntryDialog` `existing` keyed only on the name *(Low)*

If the user's rules change while the dialog is open (rare), the "already allowed or blocked" state shown is stale. Key it on `(name, rulesVersion)`.

### L18: Search covers only the name and cached label *(Info)*

Search doesn't match package names or outcome. Typing `com.android` or "blocked" could be useful. This is optional.

### Positives

- RAM-only log, an LRU bound, and grouping by (uid, name, outcome).
- CSV formula-injection defusing on attacker-chosen app labels.
- Export goes only to the SAF document the user picks: no temp file, no share intent.
- Section state survives tab switches without being persisted.

## 7. Build, CI and supply chain

### M6: Keystore secrets with backslashes break `keystore.properties` *(Medium)*

The CI writes `keystore.properties` with a shell heredoc. `java.util.Properties` treats `\` as an escape character and `:`/`=` as separators, so a password containing `\` (or a leading space) is silently changed. The release then fails to sign or, worse, signs with a different alias.

Fix: write the values with escaping (`sed 's/\\/\\\\/g'`), or pass the secrets as environment variables that `build.gradle.kts` reads (`System.getenv`), which avoids the properties file in CI.

### L26: No CI on pull requests *(Low)*

`release.yml` runs on push to `main` and on manual dispatch. A broken commit is found only when it is already a release attempt. Add a `ci.yml` on `pull_request` and on non-main branches that runs `./gradlew --no-daemon test assembleDebug`, with no secrets and `permissions: contents: read`.

### L27: `versionCode` from `git rev-list --count` *(Low)*

- The workflow already uses `fetch-depth: 0` (`release.yml:35`), so CI counts the full history. Good.
- The fallback to `1` when git is unavailable means a local release build can never upgrade an installed CI build. That is probably intended, but it is worth a comment.
- A history rewrite (squash or force-push) lowers the count, and Android refuses the downgrade.

### L28: Dependencies are about two years old *(Low)*

AGP 8.7.3, Kotlin 2.1.0, Compose BOM 2024.12.01, OkHttp 4.12.0, coroutines 1.9.0, Gradle 8.11.1.

- There are no known exploitable CVEs in this usage, but OkHttp 5.x and newer Compose releases bring HTTP/2 and performance fixes.
- `targetSdk 35` is fine for sideload and F-Droid. Google Play requires API 36 for updates from around Aug 2026, which matters only if you ever publish there.
- Upgrading is a mechanical job: bump versions, regenerate `verification-metadata.xml` (re-adding the Linux `aapt2` entries), and run tests.

### L29: An empty `proguard-rules.pro` is fine, with one caveat *(Info)*

R8 full mode, the default in AGP 8, plus `org.json` and OkHttp works without rules. Check that `ResolverIcon`'s explicit `when` (which survives shrinking) is the only reflective-looking path. Verified: no `getIdentifier` and no reflection.

### L30: Repository hygiene *(Low)*

These files are tracked but referenced nowhere:

- `README.old.md` (21 KB);
- `Wallupus.ico` (234 KB);
- `Wallupus.png` (3.3 MB).

Every clone carries them. Delete them, or move the brand sources into `androidPack/` and document them there.

### Positives

- SHA-256 verification metadata for every artifact, a pinned `distributionSha256Sum`, and SHA-pinned actions. That is better supply-chain posture than most commercial apps.
- `dependenciesInfo` excluded (F-Droid friendly). No analytics or crash SDKs.
- Signed releases only.

## 8. Tests

The suite has 55 tests across 9 classes, all of them passing: DnsMessage 13, Filter 10, LogExport 9, QueryGroups 5, IpPacket 5, CustomUpstream 4, Expansion 4, AppGroups 3, ReleaseTag 2.

Gaps, ordered by value:

1. **`DnsCache`.** AGENTS.md lists it as JVM-pure, and it has no dedicated test. Cover:
   - TTL expiry, and the minimum/maximum TTL clamp;
   - the LRU bound at 512;
   - `put` with a stale epoch dropped after `clear()`;
   - answer TTL rewriting (remaining TTL, not the original);
   - negative caching (NXDOMAIN with SOA minimum).
2. **`PacketLoop.handle` logic.** Extract the decision part (packet → `Blocked | CacheHit | Forward | Drop | Reset`) into a pure function, and test it with `TestPackets`. This covers matcher-before-cache order, mode switches and the cache clear on generation change.
3. **`SourceCheck` and update policy.** Cover the ¼ rule, empty-list refusal, and the shrink-pinning behaviour from M4 once it is fixed.
4. **`ListParser` edge cases.** Multi-name hosts lines (L9), CRLF, BOM, IDN/punycode, trailing dots, uppercase, inline comments (`0.0.0.0 a.com # ads`).
5. **`IpPacket` fuzz.** A seeded random-bytes loop asserting that `parseUdp` and `buildTcpReset` never throw. This is cheap insurance for the "bad packet never kills DNS" rule.
6. **`DnsMessage` fuzz.** The same idea for `parseQuery` and `isResponseFor`, which run on attacker-controlled upstream bytes (relevant to H1).

## 9. Ideas and improvements

Grouped by effort. Everything respects the existing invariants: no telemetry, tiny dependencies, nothing persisted automatically.

### Quick wins (hours)

- **Quick Settings tile** (`TileService`) to toggle blocking without opening the app. It needs no extra permission.
- **Confirm or undo on Clear**, and an **export result snackbar**.
- **Re-check Private DNS on resume**, with a button that opens network settings.
- **Pause blocking for 5 / 15 / 60 min**, a common need when a site breaks. Use a `Handler` or `AlarmManager` to flip `Modes.blocking` back.
- **Delete orphaned source caches** (L11).

### Medium (a day or two)

- **Network-change handling** (H2): pool eviction, `setUnderlyingNetworks`, plain-DNS refresh.
- **ICMP unreachable responder** for trapped IPs (L1).
- **In-flight query coalescing** (L3) and **hedged failover** (L2).
- **Per-app bypass**: `addDisallowedApplication` for apps that break, such as banking apps with certificate checks against DNS answers, or captive portals. Optionally, a per-app "log only, don't block" setting.
- **Blocked-response mode setting**: NXDOMAIN (current), `0.0.0.0`/`::`, or REFUSED. Some apps retry aggressively on NXDOMAIN, and `0.0.0.0` makes them give up faster.
- **`$important` precedence** over list `@@`, plus `$all`/`$document` acceptance in `ListParser` (L10).
- **Shrunken-list acceptance** (M4).
- **Captive portal awareness**: when `NetworkCapabilities.NET_CAPABILITY_CAPTIVE_PORTAL` is present, bypass blocking (or DoH) for the portal check, so hotel and airport Wi-Fi logins work.

### Larger

- **Minimal TCP/53 responder** (M1). This completes DNS protocol compliance.
- **mmap'd `blocklist.bin`** (L12): instant load, no heap.
- **Custom user lists by URL** (sources beyond `config.json`). This needs the same https-only and size-cap validation that `Config.load` already does.
- **Statistics view**: top blocked domains and top asking apps since boot, from the existing RAM log. Nothing persisted.
- **Local DNS overrides** (`name → IP`): a tiny hosts-style "rewrite" rule type for home-lab names. It fits the user-rules model.
- **Dependency refresh** to current AGP, Kotlin, Compose and OkHttp 5, with regenerated verification metadata.

## 10. Recommended order of work

1. **H1**: coroutine exception handlers plus catch-all → SERVFAIL. About 20 lines, and it removes the only realistic crash path.
2. **H2**: network callback with pool eviction. This is the largest user-visible latency fix.
3. **M3**: Private DNS re-check on resume.
4. **M2 / M1**: TC handling in `PlainDnsClient`, then decide on the TCP/53 responder.
5. **M4, M5, M6**: list pinning, safe export, keystore escaping.
6. Tests: `DnsCache`, then the extracted `handle` decision function, then the fuzzers.
7. A PR CI workflow, repo cleanup, then the dependency refresh.
8. Features from section 9 as interest allows. The QS tile and pause timer give the most value per hour.

## 11. What is already excellent

It is worth recording what should **not** change:

- The DNS-only, no-TCP-stack design with self-exclusion. It is small, auditable and battery-cheap.
- Matcher before cache, epoch-guarded cache writes, single-writer cache clears.
- Immutable, lock-free filter swaps, plus atomic, corruption-tolerant `blocklist.bin`.
- "Never make things worse" list updates.
- Privacy: RAM-only logs, SAF-only export, no backups, no recents screenshots, no telemetry, the update check only on tap.
- Supply-chain locking end to end.
- A DoH-bypass list that covers the Firefox canary domain and DDR (`resolver.arpa`). Most blockers miss both.
- `AGENTS.md` itself: a precise, enforced record of the system's invariants.
